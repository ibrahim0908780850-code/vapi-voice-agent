# تقرير مراجعة الجاهزية للإنتاج — SALIH AI

**تاريخ المراجعة:** 25 أغسطس 2026  
**النطاق:** مستودع `vapi-voice-agent` والواجهة الأصلية `salih-ai` المتاحة ضمن مساحة المشروع.  
**منهجية المراجعة:** جرد ثابت للمعمارية والمسارات والإعدادات، مراجعة محددة لحدود المصادقة والعزل والويبهوكات والرفع والمهام، وتشغيل مجموعة الاختبارات المحلية. لم تُقرأ قيم مفاتيح أو بيانات إنتاجية.

## الملخص التنفيذي

الخلفية واسعة الوظائف وتحتوي أساساً عملياً لتدفق الشركات متعدد المستأجرين، وتدفق التسجيل والقبول وتسجيل الدخول مغطى الآن باختبار دورة كاملة. بعد مرحلة تقوية الأمان الثانية، أغلقت المسارات الحساسة المعالجة الاعتماد على `tenant_id` القادم من العميل، وأصبح استيراد المواقع والرفع والويبهوكات وحدود الطلبات خاضعاً لحماية مخصصة. لكن المشروع ما زال في مرحلة **تطوير نشطة**؛ إذ ما زال `index.js` يخلط تشغيل Express والمسارات والعمال، وتبقى بعض المسارات الأقدم بحاجة إلى مراجعة تفويض route-by-route.

تمت معالجة أول ثغرة عالية الأولوية: لم يعد الرأس `x-tenant-id` يُستخدم لتحديد الشركة في الإنتاج. كما أضيفت حماية ملفات البيئة وتوثيق تشغيل آمن وخارطة نقل تدريجية، من دون تغيير المسارات العامة الحالية.

> **درجة الجاهزية الحالية: 7/10.** تدفقات الشركة الأساسية والحماية الرئيسية واختباراتها جيدة، لكن لا يُنصح باعتبار النظام مكتملاً قبل فصل التشغيل والعمال، والتحقق الحي من Webhooks في staging، ومراجعة المسارات القديمة المتبقية.

## ما تم فحصه

| المجال | النتيجة |
|---|---|
| الاعتماديات | Node 20.x وExpress 5 وSupabase وRedis/BullMQ وVapi/Gemini موجودة في `package.json` |
| نقطة التشغيل | `index.js` يجمع تشغيل العمال والمجدول وإعدادات Express وأكثر من مجموعة مسارات |
| تدفق الشركات | اختبارات التسجيل والطلب والقبول وتوجيه الشركة تعمل محلياً |
| الواجهة الأصلية | الملف المتاح يتصل بطبقة `api.company.request` وينتقل إلى الانتظار بعد نجاح الطلب؛ يجب تأكيد اكتمال باقي الواجهة من المستودع الأصلي عند مزامنتها |
| المصادقة | JWT مستخدم لمسارات الدخول والمنصة؛ تفويض مالك المنصة يعتمد الدور/العلم أو البريد المعرف |
| Supabase | يستخدم العميل الإداري من الخلفية؛ هذا يتطلب التزاماً صارماً بالعزل داخل كل استعلام |
| العمال | Scheduler يضيف مهام متكررة لكل شركة عند البدء، من دون مفاتيح إزالة تكرار أو إغلاق منظم ظاهر في المسار المراجع |

## المخاطر المتبقية حسب الأولوية

| الأولوية | الخطر | الأثر | المعالجة المقترحة |
|---|---|---|---|
| معالجة | استيراد الموقع ورفع ملفات المعرفة/الوسائط كانا يثقان بمعرف الشركة أو URL خارجي | انتحال شركة أو SSRF أو استنزاف موارد | أضيف JWT tenant، وسياسة رفع موحدة، وفحص DNS/IP والتحويلات والحدود |
| معالجة | Vapi وMeta والبريد لم تكن تملك تحققاً موحداً أو idempotency | تزوير Webhook أو معالجة مكررة | أضيف تحقق provider-aware ومفتاح claim عبر Redis/fallback وتوثيق متغيرات البيئة |
| عالية | `index.js` يبدأ العمال والمجدول ضمن ملف API | صعوبة الاختبار والتوسع والإغلاق المنظم | نقل إعداد التطبيق إلى `app.js` وبدء العمال/الإغلاق إلى `server.js` تدريجياً |
| عالية | scheduler يضيف وظائف متكررة لكل tenant عند البدء بلا jobId ثابت أو إزالة تكرار ظاهرة | تكرار التقارير أو الإشعارات بعد إعادة النشر | `jobId` ثابت لكل tenant/type واستراتيجية upsert وإغلاق queue/worker |
| متوسطة | الأخطاء في بعض المسارات ترجع `error.message` للعميل | كشف تفاصيل تشغيل أو مخطط بيانات | نموذج خطأ موحد وآمن مع logging منظم داخلي |
| متوسطة | CORS مضمّن في `index.js` | صعوبة بيئات متعددة وتغيير الواجهة | استخراج إعداد CORS واستخدام `FRONTEND_URL`/قائمة origins من البيئة |
| متوسطة | لا يظهر rate limiting عام لمسارات الذكاء الاصطناعي والرفع | استنزاف تكلفة/موارد | حد طلبات حسب المستخدم/الشركة والقناة، وحدود payload |

## هل يحتاج الخلفية مفتاحاً جديداً؟

لا يظهر من فحص الكود أن **تدفق الشركة الأساسي** يحتاج مفتاحاً جديداً غير مهيأ. والدليل العملي أن الخدمة وصلت سابقاً إلى أخطاء Supabase مقروءة؛ ما يعني أن اتصال Supabase والمفتاح الإداري كانا يعملان في ذلك المسار. كما أن وصول مالك المنصة إلى لوحته يعتمد إعداد `PLATFORM_OWNER_EMAIL` أو علامة الدور، لا مفتاح API جديد.

المفاتيح المطلوبة تكون **حسب الخدمة المفعلة**: `SUPABASE_SECRET_KEY` و`JWT_SECRET` للنواة، و`REDIS_URL` للمهام، و`GEMINI_API_KEY` للذكاء الاصطناعي، ومفاتيح مزودي القنوات عند تشغيلهم. إذا أظهر Railway لاحقاً رسالة `Missing <NAME>`، أضف ذلك المتغير بالاسم المذكور فقط من لوحة Variables، ولا تضعه في Git.

## خطة التنفيذ التالية

1. تنفيذ طبقة middleware موحدة: `authenticate`, `requireRole`, `requireTenant`.
2. نقل مسارات website ingestion والرفع خلف middleware الشركة، وإغلاق SSRF والتحقق من الملفات.
3. اعتماد تحقق توقيع Vapi/Meta/WhatsApp والبريد مع idempotency.
4. فصل `app.js` و`server.js` وإضافة graceful shutdown للـ HTTP وRedis وBullMQ.
5. إدخال repositories للخدمات الحرجة وإضافة اختبارات عزل شركات واختبارات تكامل للويبهوكات.

## حدود هذا التقرير

هذا فحص برمجي واختباري، لا اختبار اختراق كامل ولا مراجعة مباشرة لبيانات Supabase أو قيم Railway السرية. يجب تنفيذ اختبارات staging ببيانات معزولة قبل النشر العام.
