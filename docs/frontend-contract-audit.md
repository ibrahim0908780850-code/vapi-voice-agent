# جرد عقود الواجهة الأصلية salih-ai

## ملاحظة أولية

عند فتح `https://salih-ai-one.vercel.app/` ظهرت شاشة طلب تفعيل شركة قيد المراجعة بسبب حالة جلسة متبقية في المتصفح. لم تُدخل بيانات ولم يُجر أي طلب كتابي. لذلك سيُستخرج عقد الواجهة من كود المصدر والحزمة المنشورة ومسارات الشبكة المتاحة، لا من بيانات هذه الجلسة.

## العقود المنشورة المؤكدة

| الواجهة | الطلب | حالة الخلفية الحالية | ملاحظة التوافق |
|---|---|---|---|
| الدخول | `POST /auth/login` | موجود | يعيد token و`next_step`، وهو متوافق مع خدمة الدخول المنشورة. |
| طلب تفعيل الشركة | `POST /company/request` مع JSON وBearer token | موجود | الحزمة ترسل `company_name` و`website` و`document_url`؛ هذه الحقول مدعومة. |
| لوحة الشركة | `GET /api/dashboard/{stats,leads,calls,conversations,properties,ai-agent,company}` | موجود | prefixes موجودة؛ يلزم تثبيت عقود الأخطاء والحقول غير المتسقة في اختبار التوافق. |
| طلبات مالك المنصة | `GET/PATCH /platform/company-requests...` | غير متوافق في prefix الموافقة | الخلفية تركب المسار تحت `/api/platform` وتستخدم `POST /create-company` للموافقة بدلاً من `PATCH /company-requests/:id/approve`. |

> تُظهر الحزمة المنشورة أن إنشاء الشركة يستخدم JSON وBearer token، لا multipart. يرفع الملف أولاً ثم يمرر `document_url` إلى `/company/request`.

## عقود مصدرية إضافية تحتاج معاملة منفصلة

نسخة المصدر المحلية تحتوي صفحات CRM ووكلاء، لكنها لا تطابق بالكامل الحزمة المنشورة: تستدعي `api.agents.*` و`api.crm.*` و`api.ai.chat` رغم أن `services/api.ts` المتاح محلياً لا يعرّف هذه الوحدات. لذلك ستُعامل هذه المسارات كعقود واجهة مطلوبة للتحقق، لا كدليل وحيد على السلوك المنشور.

| المجال | العقد المتوقع من المصدر | التغطية الخلفية الحالية |
|---|---|---|
| وكلاء AI | CRUD عبر `api.agents` مع `name`, `system_prompt`, `voice_enabled`, `whatsapp_enabled`, `model`, `status` | لا توجد طبقة `agents` متوافقة ظاهرة؛ يوجد ملخص dashboard فقط. |
| محادثات CRM | قائمة محادثات ورسائل وإرسال `api.ai.chat` | `crm` يوفّر ملاحظة فقط و`ai_gateway` لا يوفّر `/chat` متوافقاً. |
| لوحة الشركة المصدرية | تستدعي `api.dashboard.agent()` بالمفرد | الخلفية توفّر `/api/dashboard/ai-agent`؛ الحزمة المنشورة تشير إلى `agents()` بالجمع، لذا يلزم alias متوافق لا تغيير الواجهة. |

## نتيجة المقارنة

| الأولوية | فجوة التوافق | القرار |
|---|---|---|
| حرجة ومؤكدة | الواجهة المنشورة تستدعي `/platform/company-requests/:id/approve` بينما الخلفية كانت تملك فقط `/api/platform/create-company` | أضيف alias `/platform` ومسار `PATCH /company-requests/:id/approve` مع اختبار HTTP. |
| متوسطة ومؤكدة | بعض صفحات المصدر تستدعي `api.dashboard.agent()` | أضيف `GET /api/dashboard/agent` كـalias لـ`/api/dashboard/ai-agent` مع بقاء المسار الأساسي. |
| غير قابلة للتنفيذ من الخلفية وحدها | صفحات المصدر تستدعي `api.agents`, `api.crm`, `api.ai`, `api.knowledge`, `api.team`, `api.settings`, `api.reports`، لكن `client/src/services/api.ts` لا يعرّف هذه الوحدات أو مساراتها | يجب تثبيت أو استعادة ملف API كامل من نسخة واجهة مرجعية قبل بناء aliases؛ تخمين مساراتها سيخلق عقداً جديداً غير مضمون. |
| خارج الحزمة المنشورة الحالية | الحزمة المنشورة تشير فقط إلى auth، company request، dashboard، وطلبات المنصة | تركز هذه الجولة على العقود المؤكدة في الحزمة حتى لا يضاف سلوك غير مستخدم أو تنكسر الواجهة الحالية. |

## تحقق التوافق المحلي

نجحت اختبارات HTTP المحلية لمسار موافقة المنصة المنشور وalias `/api/dashboard/agent` بعد مصادقة Bearer صالحة وملف مستخدم تابع للشركة. أعاد alias الوكلاء مصفوفة الوكلاء نفسها التي تقبلها واجهة `salih-ai` المصدرية. بلغ إجمالي اختبارات الخلفية بعد هذه الجولة **72 اختباراً ناجحاً** دون اتصال ببيئات حية أو بيانات عملاء.

بدأ الخادم محلياً بعد التعديلات باستخدام قيم بيئة اختبار غير حساسة وظهر سجل تشغيل التطبيق والعمال والمجدول بنجاح. لم يُنفذ تحقق حي ضد Railway لأن فرع التوافق لم يُنشر إلى بيئة منفصلة، ويظل ذلك جزءاً من مسار staging المؤجل.
